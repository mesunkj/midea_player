# 📋 規格書：基於檔名與目錄結構的 Viewport 偵測結果複用機制

## 1. 任務背景與目錄結構

系統的資料夾階層通常包含多個「主題」與底下的「Model」資料夾，例如：

* `主題 A / Model A / 001.jpg`, `002.jpg` ... (約 100 張)
* `主題 A / Model B / 001.jpg`, `002.jpg` ... (約 100 張)
* `主題 B / Model X / 001.jpg` ...

**核心特性**：不同 Model 底下的圖片雖然位於不同子目錄，但**內部檔名完全相同**（例如各 Model 底下都有 `001.jpg`、`002.jpg`），且其畫面構圖與人臉位置高度相似或一致。因此，**「只要偵測過其中一個 Model 的圖片，同主題下其他 Model 的相同檔名圖片即可直接複用該結果」**，無須重複執行 AI 辨識。

---

## 2. 系統功能與邏輯調整需求

### 2.1 資料庫設計擴充（支援檔名級別快取）

* 調整 `viewport_db.json` 或資料庫索引鍵（Key）的對應邏輯。
* 除了原本用「完整檔案路徑（Full Path）」作為 Key 之外，需支援以「檔名（Filename）」**或**「相對於主題目錄的相對路徑」作為對照依據。
* 當系統準備對某個新 Model 的圖片進行掃描或載入時：
1. 檢查該檔名是否已經存在於同一個「主題（Theme）」或全域快取資料庫中。
2. 若已存在（代表其他 Model 已經偵測過同檔名檔案），則**直接複用**該筆資料（包含 `unchanged`、`zoomed`、`unrecognized` 狀態與對應的 Viewport）。
3. 若完全找不到記錄，才實際執行 AI 辨識。



### 2.2 掃描流程優化（Scan Optimization）

* 當使用者對整個主題或多個 Model 進行批次掃描時：
* **優先比對快取**：掃描到圖片時，先檢查資料庫是否已有相同檔名的處理記錄。
* **減少重複運算**：若同檔名已在先前被分析過（例如 Model A 的 `001.jpg` 已分析過），Model B 的 `001.jpg` 直接帶入快取結果，跳過 TinyFaceDetector。
* **狀態獨立記錄**：雖然複用結果，但在資料庫中仍需正確對應到各個 Model 的完整檔案路徑，確保後端讀取和前端渲染時不會出錯。
